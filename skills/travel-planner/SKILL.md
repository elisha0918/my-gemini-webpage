# 旅行規劃助手

這個 skill 的目標，是把一次模糊的「我想去某個地方玩」變成一份**別人也看得懂、自己也改得動**的行程表。

核心哲學：使用者不該被要求先想清楚所有細節才能開始。他們丟一句話，你負責問對問題、查對資料、把結果收在一個固定的地方。

---

## 先決條件

**開始查任何資料之前，先做這件事。** 用 connector 列表工具確認下面三項有沒有到位。缺了就用 connector 搜尋工具找出來、建議使用者安裝，然後**等他們裝好再繼續**——先查了才發現沒地方存，等於白做。

### 必要

| 項目 | 用途 | 缺了會怎樣 |
| --- | --- | --- |
| Notion connector | 建立與更新行程主檔 | 行程只能貼在對話框裡，關掉就沒了 |
| Booking.com connector | 查住宿、比價 | 只能靠一般搜尋估價，資料不準也沒訂房連結 |
| Kiwi.com connector | 查機票 | 查不到即時票價 |
| Notion 帳號 | 存放主檔 | 免費版就夠 |

### 選配（依需求）

| 項目 | 什麼情況下需要 |
| --- | --- |
| 瀏覽器控制工具 | 要把 Instagram 珍藏夾匯入行程時。使用者還需要先在瀏覽器登入 IG |
| 排程任務功能 | 要設定每週自動更新時。通常只有桌面版應用程式有 |
| 地圖 / 天氣 connector | 需要精算通勤時間或看預報時。多數旅行用不到，不要為了裝而裝 |

### 關於機票 connector 的地區限制

有些訂票 connector 會依使用者所在地封鎖。**Expedia 對台灣地區會直接回傳 GEOFENCING 錯誤**，遇到不要重試，換 Kiwi.com。其他地區可能有不同限制，原則一樣：一個查不到就換一個，並告訴使用者原因——否則他們會以為是自己設定錯了。

### 開場的檢查方式

第一次對話時，用類似這樣的方式帶過，不要變成冗長的審核：

> 開始之前先確認一下工具：你已經有 Notion 和 Booking.com 了，還缺一個查機票的。我建議裝 Kiwi.com，裝好跟我說一聲。

確認完就直接進入下面的流程。

---

## 為什麼要有「主檔」

聊天視窗會捲走，行程不會只排一次。所以第一件事是**建立一頁 Notion，之後所有產出都寫進去**——不要只把行程貼在對話框裡。

這樣做的好處，值得讓使用者知道：

- 他們用手機也能改（手機版 Claude 一樣能查資料、一樣能寫 Notion）
- 朋友點連結就能看，不用你重新整理一份
- 下次修改時，你有個明確的地方可以讀取現況、增量更新

如果使用者問「桌機版還是手機版比較好」，答案是：**都可以，因為主檔在雲端**。建立和大幅改動用桌機比較順，出門在外用手機補充。電腦不需要一直開著。

如果使用者提到想做「儀表板」或更漂亮的呈現——先確認 Notion 是不是已經夠用。多數情況是夠的，先把內容做對比較重要。

## 流程

### 步驟 1：問清楚條件（但一次只問重點）

使用者通常只會給你日期和人數。用提問工具一次補齊四件事：

1. **主要城市／範圍** — 決定住宿位置和交通方式
2. **這趟的重點** — 美食？購物？景點？放鬆？決定行程密度
3. **住宿預算** — 每晚每間房
4. **IG 珍藏分類的名稱** — 見下方說明

不要一次問十題。問完這四個就足以開始，其他細節可以邊做邊確認。

#### 為什麼 IG 珍藏分類要在這一步就問

因為**口袋名單會改變行程長什麼樣**。使用者存的那十幾家店分布在哪幾區，直接決定你怎麼分配每一天的區域。等行程排完才問，等於要把已經排好的動線拆掉重排——雙倍的工，而且使用者要多等一輪。

問法要明確，一次問到位：

> 你 IG 有沒有存想去的店？如果有，珍藏分類叫什麼名字？（IG → 個人頁 → 書籤圖示，分類名稱就在那）

**一定要讓使用者自己說出名稱。** 不要猜、不要自己去把清單撈回來看。每個人的命名都不一樣——「旅遊」「travel」「想去的地方」「韓國」「口袋名單」都有可能，有些人根本沒分類。使用者看一眼就知道，一秒回答；你去撈則要花好幾輪。

如果使用者說沒有、或說不用，就跳過整個 IG 流程，直接往下走。

### 步驟 2：查機票

列出 3–4 個方案，用表格呈現：去程時間、回程時間、兩人（或實際人數）總價。

**這一步最有價值的不是價格，是判斷。** 最便宜的方案常常代價很高——深夜抵達等於第一天報銷，凌晨紅眼班機等於第一天沒體力。明確講出來：

> 最便宜的省 NT$2,300，但晚上 9:45 才落地，第一天只剩吃宵夜的時間。

使用者自己看價格表看不出這件事，這是你該補上的視角。

**特別注意回程日期的陷阱。** 比價工具常把「回程當天凌晨起飛」當成正常結果排在前面，價格看起來很漂亮。但 9/19 00:30 起飛，實際上只玩到 9/18 晚上，整整少一天。看到回程時間在 00:00–06:00，一定要明講。

### 步驟 3：查住宿

篩出 4 間符合預算的，附上可直接點的訂房連結、評分、位置說明。位置要跟行程呼應——如果重點是購物，就找商圈步行可達的。

順手算一下：4 晚總價 ÷ 晚數 ÷ 人數，讓使用者知道實際落在預算的哪個位置。訂房工具回傳的價格通常是**整段住宿總價**，不是每晚，換算過再呈現。

### 步驟 4：排每日行程

寫進 Notion，每天一個表格：時間、行程、備註。

如果步驟 1 拿到了 IG 珍藏分類名稱，**先做完 IG 匯入再排行程**（做法見下一節），這樣一次就排到位。

**動線比景點清單重要。** 同一天的地點要在同一區，不要早上在城西、下午跑城東、晚上又回城西。排完自己檢查一遍，問自己「這樣走要花多少通勤時間」。

**第一天的密度要跟著航班走。** 紅眼班機清晨抵達 = 有完整一天但沒體力，行程要排鬆、中間留補眠時段；晚班機抵達 = 那天基本只剩晚餐。

除了每日行程，同一頁還要有：

- **行前必辦清單**（簽證／電子入境卡、交通卡、網路、換匯、App）
- **預算試算**（機票、住宿、餐飲、交通，每人小計）
- **想去清單**（排不進去的先放這裡，不要丟掉）

### 步驟 5：主動問「還有沒有想去的」

排完之後主動問一次。除了 IG，使用者常常還有存在心裡、記事本、或朋友推薦的口袋名單，但不會主動提。

如果他們給了新的地點，重新安插進行程時**仍然要顧動線**——不要為了塞進去而破壞原本的路線。

## 進階：把 Instagram 珍藏夾變成行程

這是最有價值但最少人想到的一步。很多人 IG 存了幾十則「以後要去」的店，存完就忘了。

### 前提

使用者需要在瀏覽器登入 Instagram，並且你有瀏覽器控制工具可用。沒有的話，請他們把清單截圖或貼過來。

珍藏分類的名稱應該在**步驟 1 就已經問到**。如果還沒問，先回去問，不要自己開始找。

### 首選做法：用 IG 自己的內部 API

**不要靠掃 DOM 找珍藏分類。** 珍藏夾頁面的格子是延遲載入的，實測即使捲到底、等十幾秒，`a[href*="/saved/"]` 仍可能回傳 0 個結果——你會以為使用者沒有那個分類，然後給出錯誤結論。

正確做法是在 instagram.com 的頁面上（同源才有登入 session）用 JavaScript 呼叫 IG 自己的 API。這是使用者已登入的帳號讀自己的資料，快、準、幾乎不花 token。

**步驟 A — 取得帳號**：直接問使用者，或開 `instagram.com/accounts/edit/` 後執行：

```js
await new Promise(r => setTimeout(r, 2500));
(document.documentElement.innerHTML.match(/"username":"([^"]+)"/) || [])[1] || 'NO_USERNAME'
```

**步驟 B — 列出所有珍藏分類與其 ID**：導航到 `instagram.com/<帳號>/saved/`，然後執行：

```js
await (async () => {
  try {
    const r = await fetch('/api/v1/collections/list/?collection_types=["ALL_MEDIA_AUTO_COLLECTION","MEDIA","AUDIO_AUTO_COLLECTION"]',
      { headers: { 'X-IG-App-ID': '936619743392459' } });
    const j = await r.json();
    return JSON.stringify((j.items || []).map(i => [i.collection_name, i.collection_id]));
  } catch (e) { return 'ERR ' + e.message; }
})()
```

回傳的是 `[["所有貼文","ALL_MEDIA_AUTO_COLLECTION"],["分類名稱","<一串數字 ID>"],...]`。從裡面找使用者說的那個名稱，記下它的 collection_id。

如果回傳 ERR 或空陣列 → 多半是沒登入，請使用者先在瀏覽器登入 Instagram，不要改用其他方式硬闖。

**步驟 C — 一次抓回該分類的所有貼文內文**：

```js
await (async () => {
  const ID = '<上一步拿到的 collection_id>';
  const out = []; let max = null;
  for (let p = 0; p < 6; p++) {
    const r = await fetch('/api/v1/feed/collection/' + ID + '/posts/?count=50' +
      (max ? '&max_id=' + encodeURIComponent(max) : ''),
      { headers: { 'X-IG-App-ID': '936619743392459' } });
    const j = await r.json();
    for (const it of (j.items || [])) {
      const m = it.media || it;
      const cap = (m.caption && m.caption.text || '')
        .replace(/#[^\s#]+/g, '').replace(/\s+/g, ' ').trim();
      out.push(m.code + ' :: ' + cap.slice(0, 130));
    }
    if (!j.more_available) break;
    max = j.next_max_id;
  }
  return out.join('\n---\n');
})()
```

這一段一次就把所有貼文的「編號 + 內文摘要」拿回來，不需要一則一則點開切換。三個省 token 的設計：

- **濾掉 hashtag**——IG 貼文的標籤常佔內文三分之一，但幾乎不含地點資訊
- **截到 130 字**——店名、地鐵站通常都在前段
- **一次分頁抓完**——不用逐則導航

**如果單則回傳被截斷**：改成 `out.slice(起, 迄)` 分批取回，不要重跑整段。真的需要某一則的完整內文，再單獨用 `slice(0, 400)` 重讀那一則。

### 備援做法：逐則開啟貼文

只有在 API 回傳失敗時才用。導航到 `instagram.com/p/<代碼>/`，用左右方向鍵切換，每則執行：

```js
const h1 = document.querySelector('article h1');
const t = h1 ? h1.innerText.replace(/#[^\s#]+/g, '').replace(/\n{2,}/g, '\n').trim() : '(none)';
location.href + '\n' + t.slice(0, 400)
```

**用 `article h1` 而非整頁文字擷取**——`get_page_text` 或 `document.body.innerText` 會把數十則留言一起抓回來，常是有用內容的十倍以上。把多則的切換與擷取批次送出，不要一則一個來回。

### 幾種常見情況

| 情況 | 怎麼處理 |
| --- | --- |
| 相關內容散在多個珍藏夾 | 問使用者要不要都讀，可以一起處理。查完分類清單後，順便提一下還有哪些看起來相關 |
| 完全沒分類，全在「所有貼文」 | 用 `ALL_MEDIA_AUTO_COLLECTION` 當 ID。先提醒量可能很大，讀取時積極略過無關內容 |
| 使用者堅持有、你卻找不到 | **相信使用者**。八成是沒登入或方法問題，回去檢查上面的步驟，不要反覆質疑他們 |

### 挑出有用的內容

從內文中挑出：店名、地址、地鐵站、營業時間、為什麼值得去。忽略與目的地無關的貼文（其他國家、料理教學、生活小技巧、旅行小物開箱）。

有些貼文不是地點但很有用——電子入境卡、機場快速通關、當地觀光預付卡——這些歸到「行前必辦」或「實用小知識」，不要當成無關丟掉。

重新編排行程，把新地點按地理位置塞進對應的日子。**來自 IG 的項目前面加 ⭐**，讓使用者一眼看出哪些是自己存的。

### 記錄已處理的貼文

在 Notion 頁面底部維護一個區塊，記錄已經看過的貼文編號。每則 IG 貼文網址裡都有一段唯一編號（例如 `instagram.com/p/XXXXXXXXXXX/` 裡的 `XXXXXXXXXXX`）。

**判定為無關的也要記錄**，否則每次自動更新都會重讀它們。

這個清單是後續自動更新的基礎——沒有它，每次更新都得重讀全部。

## 進階：設定自動更新

如果使用者希望 IG 有新收藏時行程能自動跟上，用排程任務來做。

**先講清楚一件事：Notion 的按鈕做不到。** Notion 按鈕只能執行 Notion 內部動作（新增頁面、改屬性），沒有辦法觸發外部的 AI 流程。使用者常會這樣問，直接說明比較好。

### 排程任務的關鍵設計：先檢查、再動作

天真的做法是每次執行都重讀所有貼文——即使一則都沒新增。這很浪費。

改成兩階段：

**階段一（一定要先做完）**

1. 讀取 Notion 頁面底部的已處理編號清單
2. 導航到 `instagram.com/<帳號>/saved/`，用一段 JavaScript 一次抓回珍藏夾裡所有貼文編號（**只要編號、不要內文**，回傳極短）：

   ```js
   await (async () => {
     const ID = '<珍藏分類的 collection_id>';
     const ids = []; let max = null;
     for (let p = 0; p < 6; p++) {
       const r = await fetch('/api/v1/feed/collection/' + ID + '/posts/?count=50' +
         (max ? '&max_id=' + encodeURIComponent(max) : ''),
         { headers: { 'X-IG-App-ID': '936619743392459' } });
       const j = await r.json();
       for (const it of (j.items || [])) ids.push((it.media || it).code);
       if (!j.more_available) break;
       max = j.next_max_id;
     }
     return ids.length + ':' + ids.join(',');
   })()
   ```

3. 比對兩份清單。**沒有新編號就直接回報並結束**，不要進入階段二。

**階段二（只在有新貼文時執行）**
只讀新的那幾則（用上面步驟 C 的程式碼，把迴圈換成只抓新編號那幾則），更新行程，把新編號補進記錄。

這個設計在沒有新貼文的週次可以省掉八成以上的工作量。寫排程任務的提示詞時，要明確寫出「階段一沒發現新貼文時，絕對不要進入階段二」——否則模型容易「順手」多做。

### 排程任務提示詞要自足

排程執行時沒有原本的對話記憶。提示詞裡必須包含：

- Notion 頁面的 page_id 和標題
- **IG 帳號、珍藏分類名稱、collection_id**（寫死在提示詞裡，不要讓未來的執行去猜是哪一個）
- 要用哪些工具（工具名稱寫出來）
- 上面那兩段 JavaScript
- 輸出格式與回報方式
- 使用者的語言偏好

**這些寫死的個人資料只存在使用者自己電腦上的排程任務裡，不會跟著 skill 分享出去——所以該寫死就寫死。** 反過來說，skill 本身絕對不要留任何真實帳號、collection_id 或 page_id。

行程換了一趟新的（或重建了 Notion 頁），記得回頭更新排程任務的 page_id，否則它會安靜地更新到舊頁面上。

也提醒使用者：排程任務需要應用程式開著才會執行，第一次建議手動跑一次，把工具權限先授權好。

## 省資源的做法

規劃一趟旅行會產生大量中間資料——搜尋結果、網頁內容、頁面截圖。這些都會佔用可用的上下文空間，而空間用完時對話品質會下降，使用者也得重開一輪。以下幾點影響最大，值得養成習慣。

### 最貴的浪費是「查錯了還要重來」

比截圖更貴的，是自信地查錯方向、回報錯誤結論、被使用者糾正、然後整段重做。這一輪來回的成本是原本正確做法的好幾倍，而且會消耗使用者的信任。

避免的方法：

- **有官方 API 就別掃 DOM。** 現代網頁的內容多半是動態渲染的，DOM 查詢受載入時機影響，同一段程式碼今天能跑明天就不行。同站的 API 回傳結構穩定得多。
- **選擇器要精準，不要用整頁文字反推結構。** 頁面上長得像的東西很多，`innerText` 分不出來，DOM 屬性（href、role、data-\*）分得出來。
- **抓不到結果時，先假設是方法問題，不是資料問題。** 查詢回傳空的，第一個念頭應該是「還沒載完」或「選錯方法」，不是「不存在」。
- **使用者說有、你查不到時，相信使用者。** 這是你的方法有問題的訊號，不是他們記錯了。
- **不確定的結論不要用肯定語氣說。** 「你沒有這個分類」和「我目前抓不到這個分類，可能是載入問題」是兩件事。

### 截圖是最貴的一種資訊

一張截圖的成本相當於好幾百字的文字。**能用文字取得的資訊，就不要截圖。**

| 想知道什麼 | 用什麼 |
| --- | --- |
| 頁面上有哪些連結、按鈕 | 讀取頁面結構（accessibility tree），或用 JavaScript 直接查詢 |
| 頁面文字內容 | 文字擷取工具或 JavaScript |
| 操作有沒有成功 | 看工具回傳的網址變化，通常就夠判斷 |
| 版面長什麼樣、元素在哪個座標 | 這時才截圖 |

實務上，一次 IG 匯入如果靠截圖找路，可能花掉十幾張；改用 API 查詢幾乎不花成本。

例外：**當你連續兩次用 JavaScript 都拿到不合理的結果**，截一張圖確認版面比繼續盲猜便宜。一張圖 vs. 五輪錯誤查詢，選前者。

### 不要重複讀取 Notion 頁面

行程頁會越長越大，每次完整讀取都要付一次代價。

- 你剛寫進去的內容，自己記得，不需要讀回來確認
- 要改某個段落時，用**針對性的字串取代**，不要整頁重寫
- 只有在真的不確定現況時（例如隔了很久、或使用者自己改過）才完整讀取一次

### 搜尋前先問清楚，不要邊搜邊改條件

訂房和機票的搜尋結果都很龐大——一次住宿搜尋可能回傳十間房、每間附帶數十項設施清單。重跑一次的成本不低。

所以**條件要先問齊再搜**：目的地、日期、人數、預算上限、評分下限。加上價格與評分的篩選條件，回傳的結果會少很多，也更好用。

如果使用者看完想調整，先確認他們真正想改的是什麼，再重跑——不要每聽一句就重搜一次。

### 工具一次載齊

如果環境需要先載入工具才能使用，把這一輪預期會用到的**全部寫在同一次請求裡**。一次一個地載，來回次數會累積成可觀的成本。

### 產出寫進 Notion 就好，不要在對話裡重印一遍

行程表、比價表已經寫進 Notion 了，回覆時給連結加兩三句重點即可。把整份表格再貼一次到對話框，等於同樣內容付兩次錢，而且使用者也不會在對話框裡看行程。

### 自動更新一定要「先檢查、再動作」

這是長期下來省最多的一項，做法見上一節。沒有新貼文的週次可以省掉八成以上的工作量。

## 隱私提醒

如果使用者打算把行程或流程公開分享，主動檢查一遍有沒有這些內容：

- 真實姓名
- **確切的出發與回程日期**——這等於公告自己那幾天不在家，是最容易被忽略的一項
- 住宿名稱與訂房代號
- 航班編號、訂位代號
- 個人帳號（IG 帳號、email）、珍藏夾 ID、Notion page_id

發現了就告訴使用者哪些項目風險比較高，並提議替換（例如日期改成「五天四夜」、姓名移除）。不要自己默默改掉，也不要默默留著。

## 溝通原則

- **不要要求使用者一次講清楚。** 一句話開場，你來問問題，他們選選項。
- **每個階段做完先給看。** 機票查完先確認，再去查住宿。不要一口氣做完才呈現。
- **被糾正時直接調整。** 使用者說「你找錯地方了」「你沒用某某工具」，這是有效資訊，順著改就好，不需要重新開始。也不要花一整段道歉——講清楚哪裡錯了、怎麼修，然後動手。
- **不確定的結論不要用肯定語氣說。** 前者說錯會讓使用者去懷疑自己的資料。
- **主動提出更好的做法。** 如果使用者想做的事有更簡單的替代方案（例如想做儀表板但 Notion 已經夠用），說出來。省下的力氣可以花在行程本身。
- **配合使用者的語言。** 使用者用什麼語言，Notion 頁面就用什麼語言。

## Notion 頁面建議結構

```
[目的地][天數] · [日期範圍]（[人數]）
├── 行前資訊（日期、人數、主題、預算、天氣）
├── 必辦事項（勾選清單）
├── 機票候選（比價表 + 訂票連結 + 推薦理由）
├── 住宿候選（比價表 + 訂房連結）
├── Day 1 ~ Day N（每天一個時間表）
├── 想去清單（還沒排進去的）
├── 實用小知識（入境、交通卡、退稅…）
└── 已收錄的 IG 貼文（供自動更新比對用）
```

這個結構不是硬性規定，但涵蓋了實際會用到的東西。依旅行類型調整——商務出差可能不需要「想去清單」，長期旅居可能需要加「洗衣、採買」之類的區塊。
